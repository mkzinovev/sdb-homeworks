## Ответ задание 1. Проектирование модели данных по Excel-отчёту

### 1. Анализ исходного файла

В исходном Excel-отчёте одна таблица содержит данные о сотрудниках, должностях, подразделениях, филиалах и проектах.

Исходные столбцы:

| Столбец в Excel | Что хранится |
|---|---|
| ФИО сотрудника | Фамилия, имя и отчество сотрудника |
| Оклад | Текущий оклад сотрудника |
| Должность | Название должности |
| Тип подразделения | Вид структурной единицы: группа, отдел, департамент |
| Структурное подразделение | Название подразделения |
| Дата найма | Дата приёма сотрудника на работу |
| Адрес филиала | Адрес филиала / офиса |
| Проект на который назначен | Один или несколько проектов сотрудника |

В отчёте есть повторяющиеся данные: должности, типы подразделений, подразделения, адреса филиалов и проекты. Поэтому исходную таблицу нужно разбить на несколько связанных таблиц.

Отдельно важно поле `Проект на который назначен`: у некоторых сотрудников указано несколько проектов через запятую. Это означает, что между сотрудниками и проектами нужна связь «многие ко многим» через промежуточную таблицу.

## 2. Полученная модель данных

В модели используется 7 таблиц:

1. `employees` — сотрудники.
2. `positions` — должности.
3. `department_types` — типы подразделений.
4. `departments` — структурные подразделения.
5. `branches` — филиалы / офисы.
6. `projects` — проекты.
7. `employee_projects` — связь сотрудников и проектов.

---

## 3. Описание таблиц

### Таблица `positions`

Хранит справочник должностей сотрудников.

| Столбец       | Тип PostgreSQL | Назначение         |
| ------------- | -------------- | ------------------ |
| `position_id` | `SERIAL`       | Первичный ключ     |
| `name`        | `VARCHAR(150)` | Название должности |

Первичный ключ: `position_id`.

---

### Таблица `department_types`

Хранит типы подразделений: группа, отдел, департамент.

| Столбец | Тип PostgreSQL | Назначение |
|---|---|---|
| `department_type_id` | `SERIAL` | Первичный ключ |
| `name` | `VARCHAR(50)` | Название типа подразделения |

Первичный ключ: `department_type_id`.

---

### Таблица `departments`

Хранит структурные подразделения компании.

| Столбец | Тип PostgreSQL | Назначение |
|---|---|---|
| `department_id` | `SERIAL` | Первичный ключ |
| `name` | `VARCHAR(200)` | Название структурного подразделения |
| `department_type_id` | `INTEGER` | Ссылка на тип подразделения |

Первичный ключ: `department_id`.

Внешний ключ: `department_type_id` ссылается на `department_types.department_type_id`.

---

### Таблица `branches`

Хранит адреса филиалов / офисов.

| Столбец | Тип PostgreSQL | Назначение |
|---|---|---|
| `branch_id` | `SERIAL` | Первичный ключ |
| `address` | `TEXT` | Адрес филиала |

Первичный ключ: `branch_id`.

---

### Таблица `employees`

Хранит основные данные о сотрудниках.

| Столбец         | Тип PostgreSQL   | Назначение              |
| --------------- | ---------------- | ----------------------- |
| `employee_id`   | `SERIAL`         | Первичный ключ          |
| `last_name`     | `VARCHAR(100)`   | Фамилия сотрудника      |
| `first_name`    | `VARCHAR(100)`   | Имя сотрудника          |
| `middle_name`   | `VARCHAR(100)`   | Отчество сотрудника     |
| `salary`        | `NUMERIC(12, 2)` | Оклад сотрудника        |
| `hire_date`     | `DATE`           | Дата найма              |
| `position_id`   | `INTEGER`        | Ссылка на должность     |
| `department_id` | `INTEGER`        | Ссылка на подразделение |
| `branch_id`     | `INTEGER`        | Ссылка на филиал        |

Первичный ключ: `employee_id`.

Внешние ключи:

- `position_id` ссылается на `positions.position_id`;
- `department_id` ссылается на `departments.department_id`;
- `branch_id` ссылается на `branches.branch_id`.

---

### Таблица `projects`

Хранит список проектов.

| Столбец | Тип PostgreSQL | Назначение |
|---|---|---|
| `project_id` | `SERIAL` | Первичный ключ |
| `name` | `VARCHAR(250)` | Название проекта |

Первичный ключ: `project_id`.

---

### Таблица `employee_projects`

Промежуточная таблица для связи сотрудников и проектов.

| Столбец       | Тип PostgreSQL | Назначение           |
| ------------- | -------------- | -------------------- |
| `employee_id` | `INTEGER`      | Ссылка на сотрудника |
| `project_id`  | `INTEGER`      | Ссылка на проект     |

Первичный ключ: составной — `employee_id`, `project_id`.

Внешние ключи:

- `employee_id` ссылается на `employees.employee_id`;
- `project_id` ссылается на `projects.project_id`.

---

## 4. Связи между таблицами

| Связь | Тип связи | Пояснение |
|---|---|---|
| `positions` → `employees` | 1 ко многим | Одна должность может быть у многих сотрудников |
| `department_types` → `departments` | 1 ко многим | Один тип подразделения может быть у многих подразделений |
| `departments` → `employees` | 1 ко многим | В одном подразделении может работать много сотрудников |
| `branches` → `employees` | 1 ко многим | В одном филиале может работать много сотрудников |
| `employees` → `employee_projects` | 1 ко многим | У одного сотрудника может быть несколько записей о проектах |
| `projects` → `employee_projects` | 1 ко многим | Один проект может быть связан с несколькими сотрудниками |
| `employees` ↔ `projects` | многие ко многим | Реализовано через таблицу `employee_projects` |

---

## 5. Почему модель разбита именно так

Исходный Excel-файл представляет собой плоский отчёт. Если оставить данные в одной таблице, будут проблемы:

- должности будут многократно повторяться;
- адреса филиалов будут дублироваться;
- названия подразделений будут дублироваться;
- проекты неудобно анализировать, потому что в одной ячейке может быть несколько проектов;
- при изменении названия должности, проекта или подразделения придётся менять много строк.

Поэтому справочные сущности вынесены в отдельные таблицы, а связь сотрудников с проектами вынесена в отдельную таблицу `employee_projects`.
