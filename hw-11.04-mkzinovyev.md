## Задание 1. Установка RabbitMQ

На виртуальной машине `srv01` был установлен RabbitMQ. После установки был включён management plugin и выполнен вход в веб-интерфейс RabbitMQ.

Основные команды:

```bash
sudo systemctl enable --now rabbitmq-server
sudo rabbitmq-plugins enable rabbitmq_management
sudo systemctl restart rabbitmq-server
```

Для входа в веб-интерфейс был создан пользователь `admin` с правами администратора:

```bash
sudo rabbitmqctl add_user admin admin
sudo rabbitmqctl set_user_tags admin administrator
sudo rabbitmqctl set_permissions -p / admin ".*" ".*" ".*"
```

Веб-интерфейс RabbitMQ доступен по адресу:

```text
http://192.168.56.11:15672
```

Результат: вход в RabbitMQ Management UI выполнен успешно.

## Задание 3. Подготовка HA-кластера

Была создана вторая виртуальная машина `srv02`, после чего на обеих нодах был установлен RabbitMQ.

Для корректного разрешения имён в `/etc/hosts` были добавлены записи:

```text
192.168.56.11 srv01
192.168.56.12 srv02
```

После этого ноды стали доступны друг другу по именам `srv01` и `srv02`.

### 3.1. Объединение нод в кластер

На второй ноде была выполнена процедура подключения к кластеру RabbitMQ:

```bash
sudo rabbitmqctl stop_app
sudo rabbitmqctl reset
sudo rabbitmqctl join_cluster rabbit@srv01
sudo rabbitmqctl start_app
```

Проверка состояния кластера на `srv01`:

```bash
sudo rabbitmqctl cluster_status
```

В выводе команды отображаются обе ноды кластера: `rabbit@srv01` и `rabbit@srv02`.

![Cluster status на srv01](./img/04-cluster-status-srv01.png)

Проверка состояния кластера на `srv02`:

```bash
sudo rabbitmqctl cluster_status
```

На второй ноде также отображаются обе ноды кластера в разделах `Disk Nodes` и `Running Nodes`.

![Cluster status на srv02](./img/05-cluster-status-srv02-full.png)

Дополнительный вывод с версиями RabbitMQ и Erlang:

![Версии RabbitMQ и Erlang в кластере](./img/15-cluster-status-running-nodes-versions.png)

### 3.2. Особенность RabbitMQ 4.2.5 и политика ha-all

В задании используется команда для старого механизма classic mirrored queues:

```bash
sudo rabbitmqctl set_policy ha-all "^" '{"ha-mode":"all","ha-sync-mode":"automatic"}'
```

На установленной версии RabbitMQ 4.2.5 эта команда не выполняется, потому что параметры `ha-mode` и `ha-sync-mode` больше не поддерживаются.

Ошибка выполнения старой команды:

![Ошибка старой политики ha-all](./img/07-old-ha-all-policy-error.png)

Для RabbitMQ 4.x был применён современный вариант высокой доступности через `quorum queues`.

Была создана policy с именем `ha-all`, применяемая к `quorum_queues`:

```bash
sudo rabbitmqctl set_policy ha-all "^" '{"delivery-limit":50}' --priority 0 --apply-to quorum_queues
```

Также для vhost `/` был задан тип очередей по умолчанию `quorum`:

```bash
sudo rabbitmqctl update_vhost_metadata "/" --default-queue-type quorum
```

### 3.3. Проверка quorum queue

Очередь `hello` была пересоздана как `quorum queue`.

В `producer.py` очередь объявлялась с параметрами:

```python
channel.queue_declare(
    queue='hello',
    durable=True,
    arguments={'x-queue-type': 'quorum'}
)
```

После запуска `producer.py` сообщение было успешно отправлено в quorum queue `hello`.

```bash
cd ~/rabbitmq-hw
python3 producer.py
```

![Отправка сообщения в quorum queue](./img/08-producer-quorum-result.png)

В веб-интерфейсе RabbitMQ видно, что очередь `hello` имеет тип `quorum`, является `Durable` и находится под действием policy `ha-all`.

![Очередь hello типа quorum в RabbitMQ UI](./img/09-quorum-queue-hello-web-ui.png)

### 3.4. Проверка через rabbitmqadmin

Для закрепления был использован `rabbitmqadmin`.

Команда проверки очереди:

```bash
rabbitmqadmin -u admin -p admin get queue='hello'
```

Особенность команды: `rabbitmqadmin get` не просто показывает сообщение, а забирает его из очереди. Поэтому после чтения очереди через `consumer.py` или `rabbitmqadmin` для повторной проверки нужно заново отправить сообщение через `producer.py`.

Первый запуск показал пустой результат, так как сообщение уже было забрано ранее:

![rabbitmqadmin get queue hello без сообщения](./img/16-rabbitmqadmin-get-empty.png)

После повторного запуска `producer.py` сообщение появилось в очереди и было получено через `rabbitmqadmin`:

![rabbitmqadmin get queue hello с сообщением](./img/17-rabbitmqadmin-get-message.png)

В выводе видно тестовое сообщение:

```text
payload: Hello Netology!
payload_bytes: 15
payload_encoding: string
redelivered: True
```

### 3.5. Получение сообщения consumer.py

После запуска `consumer.py` сообщение было успешно получено из очереди `hello`.


## Задание 4. Ansible playbook

Был подготовлен Ansible playbook, который автоматизирует установку и настройку RabbitMQ-кластера.

Playbook выполняет следующие действия:

1. настраивает hostname на каждой ноде;
2. добавляет записи `srv01` и `srv02` в `/etc/hosts`;
3. устанавливает и запускает `rabbitmq-server`;
4. включает `rabbitmq_management` plugin;
5. синхронизирует Erlang cookie между нодами;
6. объединяет ноды в кластер;
7. создаёт пользователя `admin`;
8. задаёт default queue type `quorum` для vhost `/`;
9. создаёт policy `ha-all` для `quorum_queues`.

Структура файлов в репозитории:

```text
ansible-rabbitmq/
├── inventory.ini
└── rabbitmq-cluster.yml
```

### 4.1. Проверка доступности нод Ansible

Перед запуском playbook была проверена доступность обеих нод:

```bash
ansible -i inventory.ini rabbitmq -m ping
```

Обе ноды вернули `pong`, значит Ansible успешно подключается к `srv01` и `srv02`.

### 4.2. Запуск playbook

Playbook был запущен командой:

```bash
ansible-playbook -i inventory.ini rabbitmq-cluster.yml
```

Фрагмент выполнения playbook:

![Запуск Ansible playbook](./img/11-ansible-playbook-run.png)

### 4.3. Результат выполнения playbook

Playbook завершился успешно. В итоговом `PLAY RECAP` на обеих нодах указано `failed=0`.

![PLAY RECAP Ansible](./img/12-ansible-play-recap.png)

### 4.4. Создание policy ha-all через Ansible

В playbook была создана policy `ha-all` для `quorum_queues`:

```bash

```

В выводе Ansible видно, что policy успешно создана:

