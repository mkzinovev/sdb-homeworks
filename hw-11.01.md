# Ответ задание 1. СУБД

## 1.1. Бюджетирование проектов, финансовая аналитика и прогнозирование рисков

Для этой задачи лучше всего подойдёт **реляционная СУБД**, например **PostgreSQL**, **Oracle Database** или **Microsoft SQL Server**.

Причина: бюджетирование, финансы, отчёты и риски требуют строгой структуры данных, связей между таблицами, транзакционности и целостности. В таких системах важно, чтобы данные не терялись, не дублировались и не противоречили друг другу.

Например, можно хранить:

- проекты;
    
- бюджеты;
    
- статьи затрат;
    
- договоры;
    
- платежи;
    
- плановые и фактические показатели;
    
- риски;
    
- финансовые отчёты.
    

Для такой задачи хорошо подходит **SQL**, потому что можно строить сложные аналитические запросы, отчёты, агрегации и прогнозные модели.

**Вывод:** оптимальный выбор — **реляционная СУБД PostgreSQL / Oracle / MS SQL Server**.

### 1.1.* Хеширование стало занимать длительное время, какое API можно использовать для ускорения?

Для ускорения хеширования можно использовать **Web Crypto API**, если хеширование выполняется на стороне веб-приложения или браузера.

Если речь идёт о серверной части, можно использовать нативные криптографические библиотеки и API, например:

- **OpenSSL EVP API**;
    
- **libsodium**;
    
- аппаратное ускорение процессора, например AES-NI;
    
- вынос тяжёлого хеширования в отдельные фоновые задачи или очередь.
    

**Вывод:** для веб-приложения — **Web Crypto API**, для серверной части — **OpenSSL / libsodium / аппаратное ускорение**.

---

## 1.2. Лендинги девелоперских проектов и CRM для лидов

Для лендингов лучше использовать **документоориентированную NoSQL-СУБД**, например **MongoDB**.

Лендинги могут иметь разные формы заявок: имя, телефон, email, интересующий объект, бюджет, комментарий, источник рекламы, UTM-метки и так далее. Структура таких данных может часто меняться, поэтому гибкая схема NoSQL здесь удобна.

Для CRM также можно использовать **документоориентированную СУБД**, например **MongoDB**, потому что карточка лида может содержать разные поля, историю коммуникаций, статусы, комментарии менеджеров, источники заявок и вложенные данные.

Также возможен вариант с **PostgreSQL**, если CRM требует строгой структуры, отчётности и сложных связей между клиентами, сделками, менеджерами и объектами недвижимости. Но по условию задачи нужны гибкость и скорость, поэтому MongoDB выглядит более подходящим вариантом.

**Вывод:**

- для лендингов — **MongoDB / NoSQL document database**;
    
- для CRM — **MongoDB**, либо **PostgreSQL**, если нужна строгая аналитика и транзакционность.
    

### 1.2.* Можно ли эту задачу закрыть одной СУБД?

Да, можно закрыть одной СУБД.

Лучший вариант — **MongoDB**.

Реализация может быть такой:

- отдельная коллекция `landing_leads` для заявок с лендингов;
    
- коллекция `clients` для клиентов;
    
- коллекция `deals` для сделок;
    
- коллекция `managers` для менеджеров;
    
- коллекция `communications` для истории звонков, сообщений и встреч.
    

Лендинги будут быстро записывать заявки в MongoDB, а CRM будет использовать эти же данные для дальнейшей обработки менеджерами.

**Вывод:** да, можно использовать одну СУБД — **MongoDB**, разделив данные по коллекциям.

## 1.3. База корпоративных норм, правил и обучающих материалов

Для этой задачи подойдёт **иерархическая СУБД** или простая **реляционная СУБД**.

Так как материалы сформированы согласно структуре компании, данные можно представить в виде дерева:

- компания;
    
- департаменты;
    
- отделы;
    
- направления;
    
- документы;
    
- инструкции;
    
- обучающие материалы;
    
- регламенты.
    

Если нужна простая и понятная структура, можно использовать **реляционную СУБД PostgreSQL или MySQL**. Например, создать таблицы:

- `departments`;
    
- `sections`;
    
- `documents`;
    
- `materials`;
    
- `categories`.
    

Если важна именно древовидная структура, можно использовать иерархическую модель или реализовать иерархию внутри PostgreSQL через связи `parent_id`.

**Вывод:** лучше использовать **реляционную СУБД PostgreSQL** с иерархической структурой таблиц.

### 1.3.* Можно ли использовать уже существующую СУБД из задач выше?

Да, можно использовать уже существующую СУБД.

Если в задаче 1.1 выбрана **PostgreSQL**, то для базы корпоративных норм и обучающих материалов можно создать отдельную схему или отдельный набор таблиц.

Например:

```text
schema: knowledge_base

tables:
- departments
- document_categories
- documents
- training_materials
- employee_roles
- access_rights
```

Такой подход позволит не разворачивать отдельную СУБД, а использовать уже существующую инфраструктуру.

Если ранее была выбрана MongoDB, то материалы также можно хранить в ней в виде документов, особенно если структура материалов может меняться. Но для простой корпоративной базы знаний PostgreSQL будет понятнее и надёжнее.

**Вывод:** да, можно использовать существующую PostgreSQL, создав отдельную схему или отдельную базу данных для корпоративной базы знаний.

## 1.4. Логистика, маршруты доставки и распределение курьеров

Для задач логистики лучше всего подойдёт **графовая СУБД**, например **Neo4j**.

Причина: логистика — это работа со связями. Есть объекты, склады, дороги, маршруты, курьеры, поставщики, точки доставки, ограничения по времени и расстоянию. Всё это удобно представлять в виде графа:

- вершины — склады, объекты, курьеры, точки доставки;
    
- рёбра — дороги, маршруты, расстояния, время в пути, стоимость доставки.
    

Графовая СУБД хорошо подходит для поиска кратчайших путей, оптимальных маршрутов и анализа связей.

Также можно использовать **PostgreSQL + PostGIS + pgRouting**, если нужна работа с географическими координатами, картами и маршрутами.

**Вывод:** оптимальный вариант — **Neo4j** как графовая СУБД. Альтернативный вариант — **PostgreSQL + PostGIS + pgRouting**.

### 1.4.* Можно ли подключить отдел закупок к этой СУБД?

Да, отдел закупок можно подключить к этой СУБД, потому что закупки тесно связаны с логистикой.

Например, закупкам нужны данные:

- поставщики;
    
- материалы;
    
- цены;
    
- сроки поставки;
    
- склады;
    
- объекты строительства;
    
- маршруты доставки;
    
- остатки и потребности.
    

Но лучше не смешивать всё в одну неструктурированную базу. Оптимальный вариант — сделать связку:

- логистика работает в **графовой СУБД**;
    
- закупки могут работать в **реляционной СУБД**, например PostgreSQL;
    
- между ними настроить интеграцию.
    

Например, закупки хранят договоры, счета, поставщиков и номенклатуру в PostgreSQL, а логистика использует Neo4j для маршрутов и связей.

**Вывод:** отдел закупок можно подключить, но лучше сделать связку **PostgreSQL для закупок + Neo4j для логистики**.

## 1.5.* Можно ли все задачи решить одной СУБД?

Да, все перечисленные задачи можно решить одной СУБД, если выбрать универсальное решение.

Лучший вариант — **PostgreSQL**.

Почему PostgreSQL подходит:

- поддерживает строгую реляционную модель для финансов и бюджетирования;
    
- поддерживает JSON/JSONB для гибких данных лендингов и CRM;
    
- позволяет строить иерархические структуры для базы знаний;
    
- поддерживает расширение **PostGIS** для геоданных;
    
- может использовать **pgRouting** для маршрутизации;
    
- поддерживает транзакции и целостность данных;
    
- подходит для аналитических запросов и отчётов.
    

Реализация может быть такой:

```text
PostgreSQL

schemas:
- finance
- crm
- knowledge_base
- logistics
- procurement
```

Для разных задач можно использовать разные возможности PostgreSQL:

```text
finance        — обычные реляционные таблицы
crm            — таблицы + JSONB для гибких полей
knowledge_base — иерархические таблицы с parent_id
logistics      — PostGIS + pgRouting
procurement    — реляционные таблицы для закупок
```

Но с архитектурной точки зрения лучше не всегда всё складывать в одну СУБД. Для учебного задания можно сказать, что PostgreSQL справится со всеми задачами. В реальном крупном проекте лучше использовать комбинированный подход:

- PostgreSQL — финансы, закупки, CRM, база знаний;
    
- MongoDB — гибкие данные лендингов и лидов;
    
- Neo4j — логистика и маршруты;
    
- Redis — кэш и быстрые временные данные.
    

**Итоговый вывод:**  
Технически все задачи можно решить на одной СУБД — **PostgreSQL**. Но оптимальная промышленная архитектура — это комбинация нескольких СУБД под разные типы задач.

# Ответ задание 2. Транзакции

## 2.1. Пользователь пополняет баланс счёта телефона

Для успешного завершения транзакции должны произойти следующие действия:

1. **Пользователь вводит данные для пополнения**  
    Пользователь указывает номер телефона, сумму пополнения и выбирает способ оплаты, например банковскую карту.
    
2. **Система проверяет корректность данных**  
    Проверяется, существует ли номер телефона, корректна ли сумма, доступен ли оператор связи и можно ли выполнить платёж.
    
3. **Платёжная система проверяет возможность списания средств**  
    Банк или платёжный сервис проверяет карту пользователя, наличие денег на счёте, лимиты и возможность проведения операции.
    
4. **Деньги списываются со счёта пользователя**  
    Если проверка прошла успешно, нужная сумма блокируется или списывается с банковской карты пользователя.
    
5. **Баланс телефона пополняется**  
    Оператор связи получает подтверждение платежа и увеличивает баланс указанного номера телефона на сумму пополнения.
    
6. **Система фиксирует результат транзакции**  
    В базе данных сохраняется информация об операции: номер телефона, сумма, дата, статус платежа. Пользователь получает уведомление об успешном пополнении.
    

Если все этапы выполнены успешно, транзакция считается завершённой.

Если на одном из этапов произошла ошибка, например денег на карте недостаточно или оператор связи недоступен, транзакция должна быть отменена, а деньги не должны списаться окончательно.

## 2.1.* Если пополнение счёта телефона происходит через автоплатёж

При автоплатеже действия будут похожими, но запуск операции происходит автоматически, без ручного участия пользователя.

1. **Система проверяет условие автоплатежа**  
    Например, наступила заданная дата списания или баланс телефона стал ниже установленного порога.
    
2. **Система проверяет настройки автоплатежа**  
    Проверяется номер телефона, сумма пополнения, активен ли автоплатёж, не истекла ли привязанная карта.
    
3. **Платёжная система проверяет карту и доступность средств**  
    Банк проверяет, можно ли списать деньги: достаточно ли средств, нет ли блокировок, не превышены ли лимиты.
    
4. **Происходит автоматическое списание средств**  
    Если проверка успешна, сумма автоплатежа списывается с карты пользователя.
    
5. **Оператор связи пополняет баланс телефона**  
    После подтверждения оплаты баланс номера увеличивается на сумму автоплатежа.
    
6. **Система сохраняет результат и уведомляет пользователя**  
    Информация об операции записывается в базу данных, а пользователь получает SMS, push-уведомление или email о выполненном автоплатеже.
    

Если автоплатёж не прошёл, например на карте недостаточно средств, система должна зафиксировать неуспешную попытку и уведомить пользователя. Возможно, позже будет выполнена повторная попытка списания.

## Итог

# Ответ задание 3. SQL vs NoSQL

## 3.1. Пять преимуществ SQL-систем по отношению к NoSQL

SQL-системы, например **PostgreSQL**, **MySQL**, **Oracle Database**, **Microsoft SQL Server**, лучше подходят для задач, где важны структура, надёжность и целостность данных.

### 1. Строгая структура данных

В SQL-СУБД данные хранятся в таблицах с заранее заданной структурой: строки, столбцы, типы данных, связи.

Например, в таблице `users` поле `phone` должно быть телефоном, поле `email` — строкой, а поле `created_at` — датой.

Это снижает риск хаоса в данных и делает систему более предсказуемой.

---

### 2. Поддержка транзакций

SQL-СУБД хорошо поддерживают транзакции и принцип **ACID**:

- атомарность;
    
- согласованность;
    
- изолированность;
    
- долговечность.
    

Например, если пользователь переводит деньги, важно, чтобы деньги не просто списались с одного счёта, но и были зачислены на другой. Если один из этапов не выполнен, вся операция должна быть отменена.

Для финансовых, банковских, бухгалтерских и корпоративных систем это критически важно.

---

### 3. Целостность данных

В SQL можно задавать ограничения:

- `PRIMARY KEY`;
    
- `FOREIGN KEY`;
    
- `UNIQUE`;
    
- `NOT NULL`;
    
- `CHECK`.
    

Это помогает не допустить некорректных данных.

Например, нельзя создать заказ для клиента, которого нет в таблице клиентов, если настроен внешний ключ.

---

### 4. Удобный язык запросов

SQL — это мощный и стандартизированный язык запросов. С его помощью удобно получать данные, строить отчёты, делать фильтрацию, группировку, сортировку и объединение таблиц.

Например, можно легко получить:

- сумму продаж за месяц;
    
- список клиентов с долгами;
    
- отчёт по проектам;
    
- аналитику по отделам;
    
- данные по связанным таблицам.
    

SQL хорошо подходит для аналитики и отчётности.

---

### 5. Зрелость и надёжность технологий

SQL-СУБД давно используются в промышленной эксплуатации. У них развитая экосистема:

- резервное копирование;
    
- репликация;
    
- мониторинг;
    
- разграничение прав доступа;
    
- оптимизация запросов;
    
- индексы;
    
- инструменты администрирования;
    
- большое количество специалистов на рынке.
    

Поэтому SQL-системы часто выбирают для критически важных корпоративных приложений.

---

## Вывод по 3.1

Пять основных преимуществ SQL перед NoSQL:

```text
1. Строгая структура данных.
2. Надёжные транзакции.
3. Контроль целостности данных.
4. Удобный язык SQL для запросов и аналитики.
5. Зрелость, надёжность и развитая экосистема.
```

SQL лучше подходит для систем, где данные должны быть точными, связанными и непротиворечивыми.

---

# 3.1.* Преимущества NewSQL перед SQL и NoSQL

**NewSQL** — это класс современных СУБД, которые пытаются объединить преимущества классических SQL-систем и NoSQL.

То есть NewSQL сохраняет:

- SQL-запросы;
    
- транзакции;
    
- ACID;
    
- строгую целостность данных;
    

но при этом добавляет:

- горизонтальное масштабирование;
    
- высокую производительность;
    
- распределённую архитектуру;
    
- отказоустойчивость.
    

Примеры NewSQL-систем:

```text
Google Spanner
CockroachDB
TiDB
YugabyteDB
VoltDB
```

---

## Преимущества NewSQL перед обычными SQL-системами

### 1. Горизонтальное масштабирование

Классические SQL-СУБД часто масштабируются вертикально: нужно увеличивать мощность одного сервера.

NewSQL позволяет масштабироваться горизонтально: добавлять новые серверы в кластер.

Это удобно для крупных систем с большим количеством пользователей и данных.

---

### 2. Распределённая архитектура

NewSQL изначально рассчитаны на работу в распределённой среде.

Данные могут храниться на нескольких узлах, в разных дата-центрах или регионах. Это повышает отказоустойчивость и доступность системы.

---

### 3. Высокая отказоустойчивость

Если один сервер выходит из строя, система может продолжить работу за счёт других узлов.

Для бизнеса это важно, потому что простой базы данных может остановить работу сайта, CRM, ERP или финансовой системы.

---

## Преимущества NewSQL перед NoSQL

### 1. Поддержка SQL

В отличие от многих NoSQL-решений, NewSQL поддерживает привычный SQL-язык.

Это упрощает разработку, аналитику и сопровождение системы.

---

### 2. Поддержка ACID-транзакций

Многие NoSQL-системы делают упор на скорость и масштабируемость, но могут уступать по строгой согласованности данных.

NewSQL старается сохранить надёжность транзакций, как в классических SQL-СУБД.

---

### 3. Более строгая целостность данных

NewSQL лучше подходит для систем, где нельзя допускать противоречивые данные.

Например:

- банковские операции;
    
- финансы;
    
- биллинг;
    
- заказы;
    
- складской учёт;
    
- корпоративные системы.
    

---

## Итог по 3.1.*

NewSQL можно рассматривать как компромисс между SQL и NoSQL.

```text
SQL даёт структуру, транзакции и надёжность.
NoSQL даёт гибкость и масштабируемость.
NewSQL пытается объединить оба подхода:
строгие транзакции + SQL + горизонтальное масштабирование.
```

**Вывод:** NewSQL-системы имеют преимущество там, где нужна надёжность классических SQL-баз, но при этом требуется масштабируемость и отказоустойчивость уровня распределённых NoSQL-систем.

# Ответ задание 4. Кластеры

Для такой задачи тип СУБД я бы выбирал в первую очередь по критерию **масштабируемости и возможности параллельной обработки данных**.

Если нужно выполнять большое количество вычислений на огромном объёме данных и под это выделено **1000 машин**, значит обычная классическая реляционная СУБД на одном сервере здесь не подойдёт. Главный критерий выбора — способность СУБД распределять данные и вычисления между большим количеством узлов.

## Основные критерии выбора СУБД

Я бы учитывал следующие параметры:

1. **Горизонтальное масштабирование**  
    Система должна уметь увеличивать производительность за счёт добавления новых серверов.
    
2. **Распределённое хранение данных**  
    Данные должны делиться на части и храниться на разных машинах кластера.
    
3. **Параллельная обработка**  
    Вычисления должны выполняться одновременно на множестве узлов.
    
4. **Отказоустойчивость**  
    Если часть машин выйдет из строя, задача не должна полностью остановиться.
    
5. **Работа с большими данными**  
    СУБД должна быть рассчитана на Big Data-нагрузку, а не только на обычные транзакции.
    

Для такой задачи лучше подойдут **распределённые NoSQL-СУБД** или специализированные системы для Big Data, например:

```text
Apache Hadoop / HDFS
Apache HBase
Apache Cassandra
ClickHouse
Apache Spark
```

Если данные в основном используются для аналитики, отчётов и больших вычислений, можно выбрать **колоночную распределённую СУБД**, например **ClickHouse**.

Если нужно хранить огромные объёмы данных в распределённом виде, подойдёт связка **HDFS + HBase** или **Cassandra**.

# Какая модель распределённых вычислений подойдёт лучше всего

Лучше всего здесь подойдёт модель **MapReduce**.

## Почему MapReduce подходит

MapReduce хорошо подходит для обработки огромного количества данных на большом количестве машин.

Принцип работы такой:

```text
1. Большая задача делится на множество маленьких подзадач.
2. Эти подзадачи распределяются между машинами кластера.
3. Каждая машина обрабатывает свою часть данных.
4. Затем результаты собираются и объединяются в общий итог.
```

Модель состоит из двух основных этапов:

## 1. Map

На этапе **Map** данные разбиваются на части и обрабатываются параллельно на разных серверах.

Например, если нужно обработать терабайты логов, каждый сервер получает свой фрагмент логов и выполняет над ним вычисления.

## 2. Reduce

На этапе **Reduce** промежуточные результаты собираются, группируются и сводятся в итоговый результат.

Например, можно посчитать общее количество событий, ошибок, заказов, пользователей или финансовых операций.

---

# Почему именно MapReduce

MapReduce подходит, потому что:

- хорошо масштабируется на сотни и тысячи машин;
    
- позволяет обрабатывать огромные объёмы данных;
    
- автоматически распределяет задачи по узлам;
    
- устойчив к отказам отдельных машин;
    
- хорошо подходит для пакетной обработки данных;
    
- позволяет эффективно использовать весь кластер.
    

Для кластера из **1000 машин** это особенно важно, потому что задача должна выполняться не на одном мощном сервере, а параллельно на множестве узлов.

# Итоговый ответ

Для выбора типа СУБД главным критерием будет **способность к горизонтальному масштабированию, распределённому хранению и параллельной обработке больших объёмов данных**.

Для такой задачи лучше использовать **распределённую Big Data-систему** или **распределённую NoSQL/колоночную СУБД**, например:

```text
Hadoop/HDFS + HBase
Cassandra
ClickHouse
Spark
```

А лучшая модель распределённых вычислений — **MapReduce**, потому что она позволяет разделить большую вычислительную задачу на множество независимых частей, выполнить их параллельно на 1000 машинах и затем собрать общий результат.
